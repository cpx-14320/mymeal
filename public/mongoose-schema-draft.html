Mongoose Schema 草案

延伸自 data-model-reference.html （規劃①～⑥，先讀那份了解命名規則跟決策脈絡）——這份把裡面「③ 各 Collection 詳細欄位」 轉成可以直接抄進 lib/models/ 的 Mongoose schema 程式碼。 整份都是草案，還沒有寫進專案，先給你確認欄位／命名沒問題，之後再一次動手實作＋搬資料。

① 跟現有實作的落差 ② 待你決定的事 ③ member 群組 ④ menu 群組 ⑤ 訂單與錢包 ⑥ 其他 ⑦ 確認後要做的事

01 跟現有實作的落差

這次設計前重新讀了規劃文件的命名規則，發現我這次對話裡已經動手做的 member / department / unit 三張表， 跟規劃文件的決定有幾個地方對不上。列出來讓你決定要不要照規劃文件調整。

Collection 命名：department/unit vs. member_departments/member_units
規劃文件的命名規則 08：同群組的表要共用 member_ 前綴（比照舊系統 訂餐網站資料表.xlsx 的 member_balance、member_permissions 分組習慣）。目前實作沒加前綴，用的是單數 department/unit。
member.role（自由字串）vs. member.roleKey（參照 member_roles.key）
目前 role 是自由文字，值直接存角色顯示名稱（例："超級管理員"）。規劃文件建議改成 roleKey 參照獨立的 member_roles collection，角色改名不用動 member 表，也才能真的做「後台－會員權限」那個管理頁。
member 缺少 extension（分機）、balance（錢包餘額快取）欄位
規劃文件裡這兩個欄位已經定案，目前實作沒有。balance 要等 wallet_ledger 做出來才有意義寫入，extension 現在就可以補。
department / unit 缺少 active 欄位
規劃文件：停用的部門/單位不能再被指派，但既有資料不用動（沿用歷史紀錄）。目前實作刪除部門/單位是直接刪除（已加保護：底下還有會員擋刪除），沒有「停用但保留」這個中間狀態。
這些落差都还没有强制你选——下面每張表的 schema 我先照規劃文件的版本設計（比較完整）， 有牽涉到要不要調整既有實作的地方，會在表格上方用需調整標出來。 你可以選「照規劃文件調整」或「維持現況、只把新表接上」，兩種我都能做。

02 待你決定的事

權限模型：boolean 有/無 vs. none/own/full 三段式
目前 lib/mock.ts 的 permissionCategories 跟 /admin/roles 頁面實際渲染的是 boolean 矩陣（✓ / –）。 data-model-reference.html 提案改成三段式（none/own/full），可以表達「只能看自己的」這種中間權限，但 /admin/roles 頁面的 UI 也要跟著改（現在是打勾格子，不是下拉選單）。 下面 member_roles 的 schema 先用 boolean（照現有 UI，改動範圍小），如果要換成三段式我可以重新設計。
遊戏化系統（任務／經驗值／等級）——沿用規劃文件的決定，這次不設計
daily_tasks／exp_rules／member_levels／member_experience 等表，規劃文件明確標記「還沒定案要不要做」，這份草案延續同樣的決定跳過。之後要做再說。
新發現的缺口：system_settings（系統設定）
/admin/settings 頁面（訂餐規則、Email 網域白名單、開通方式、取餐地點、公告）現在完全沒接後端，規劃文件的 17 個 collection 裡也沒有涵蓋——這份草案新增一張 system_settings（單例文件）補上，見 ⑥。

wallet_ledger（只增不改）

wallet_ledger
只增不改 儲值／消費／退款／調整都是一筆歷程，每次寫入同步更新 member.balance
type LedgerType = "topup" | "order" | "refund" | "adjustment";
type LedgerReferenceType = "group_order" | "topup_request" | "manual";

interface WalletLedgerDocument {
  _id: Types.ObjectId;
  memberId: Types.ObjectId;         // ref Member
  type: LedgerType;
  amount: number;                     // 正負號代表入帳/扣款
  balanceBefore: number;
  balanceAfter: number;                // 快照，不用每次重算
  referenceType?: LedgerReferenceType;
  referenceId?: Types.ObjectId;        // 依 referenceType 對應 group_orders._id / topup_requests._id
  note?: string;
  at: Date;
}

const walletLedgerSchema = new Schema<WalletLedgerDocument>(
  {
    memberId: { type: Schema.Types.ObjectId, ref: "Member", required: true },
    type: { type: String, enum: ["topup", "order", "refund", "adjustment"], required: true },
    amount: { type: Number, required: true },
    balanceBefore: { type: Number, required: true },
    balanceAfter: { type: Number, required: true },
    referenceType: { type: String, enum: ["group_order", "topup_request", "manual"] },
    referenceId: { type: Schema.Types.ObjectId },
    note: { type: String },
    at: { type: Date, required: true, default: Date.now },
  },
  { timestamps: false, collection: "wallet_ledger" },
);
walletLedgerSchema.index({ memberId: 1, at: -1 });
只增不改：寫入後不能再 update；要修正就再補一筆反向紀錄（例如手動調整 -95 來抵銷一筆錯誤扣款），CRUD 層不提供 update/delete 函式，只提供「新增一筆」。

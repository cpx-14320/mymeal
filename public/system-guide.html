01系統概觀

MyMeal 是公司內部的 B2E 訂餐系統重製版（原系統為 PHP + MySQL + Vue），目前這個版本是用 Next.js 重寫的 介面預覽（UI-only mock）：所有畫面、表格、篩選、分頁、彈窗都做出來了，但資料全部來自 lib/mock.ts 裡寫死或用規則產生的假資料，還沒有接資料庫、沒有真的登入系統、 後台大部分「儲存 / 刪除 / 送出」按鈕也還沒串接。這點會影響下面每一節的閱讀方式——本文件同時扮演 「現在畫面長怎樣」的操作手冊，以及「將來要接後端時，這些畫面背後應該對應什麼資料」的資料表規劃。

目前最重要的限制

components/layout/app-shell.tsx 裡的 previewMode 寫死為 true：不管有沒有登入，所有前台頁面都能自由瀏覽，側欄不鎖權限、不顯示鎖頭。 真正的權限判斷邏輯（isAuthed / isAdmin / resolveHref()）其實都已經寫好、可以運作，只是目前沒有被打開。 唯一有實際「登入狀態」效果的地方是 Header 頭像按鈕的預覽用登入切換（存在瀏覽器 localStorage，跟真正的帳號系統無關）——詳見第五節。

核心資料模型（兩條主線）

訂餐內容這條線——四層由粗到細：

  • 訂餐專區（前台一個頁面，例如「本週便當」）→ N:N 對應多個
  • 模板（例如「標準便當週」）→ 底下分自由命名的
  • 分類（例如「星期一」「飲料 / 點心」，不綁死星期幾）→ 裡面放實際的
  • 品項（品項總表裡的一筆資料，名稱／價格全站只有一份，改了就所有引用同步）

店家（供應商）跟品項類別、標籤都不是這條鏈的一層，而是掛在品項或模板上的平面標籤—— 同一個模板底下的品項可以來自不同店家。

會員與權限這條線：

  • 會員（Member）——一個真人帳號
  • 組別（MemberGroup，後台頁面標題顯示為「會員權限」）——一包權限鍵的組合，例如「餐飲管理員」
  • 權限鍵（PermissionGroup，例如 finance.topup.*）——最小可控制的功能單位，三種等級：無 / 僅限自己 / 具備

會員的 role 欄位是組別名稱字串，跟 memberGroups 動態同步，不會各自漂移。

04實際操作流程

把上面的頁面串成幾條完整的使用情境，每一步都對應到真的按鈕或欄位。

情境 A — 會員加入同事的團訂餐

開啟開團訂餐列表
前往 /group-orders，用「開放中」篩選只看還能加入的團。
點「查看 / 加入」
進入 /group-orders/[id] 團訂明細，看到截止時間、目前份數、取餐地點。
點餐
在「我的餐點」區塊用 + / − 選數量、填備註，按「送出我的訂單」。
確認訂單
回到 /orders「進行中」可看到剛加入的這筆，取消 / 修改也在這裡。

情境 B — 開一個新團

從任一入口點「開團」
/group-orders 或 /menu 頁面右上角都有這顆按鈕，連到 /group-orders/new。
選模板
挑一個已存在的模板（例如「標準便當週 / 星期三」）。
調整品項
從品項總表挑要開放的品項（可增減，不影響模板本身）。
設定成團條件
取餐時間、截止時間、成團門檻。送出後這團就會出現在 /group-orders 列表。

情境 C — 儲值與後台審核

會員申請儲值
/wallet/topup 填金額與付款方式送出，狀態顯示在 /wallet「儲值申請進度」。
後台審核人員處理
/admin/topups「待審核」頁籤逐筆核准或退件；核准後金額才計入餘額。
寫入交易明細
核准後應同步出現在 /admin/wallets「最近交易」與會員自己的 /wallet「交易明細」。
事後調整（例外情況）
金額算錯時，在 /admin/wallets 最近交易對該筆按「調整」，寫入一筆新的抵銷紀錄，不竄改原始交易。

情境 D — 後台維運「菜單」內容（由上而下）

建立 / 確認品項
/admin/items 是唯一的品項來源；分類跟標籤分別在 /admin/items/categories、/admin/items/tags 先建好。
組成模板
/admin/templates 建立分類（例如星期幾），從品項總表勾選品項放進去。
串成訂餐專區
/admin/zones 把一個或多個模板包成一個前台頁面（例如「本週便當」）。（規劃中：建立專區後應自動出現在前台左側導覽，見第八節）
開放品項才會被看到
品項 / 模板 / 專區任一層被停用，底下的內容就不會出現在前台。

情境 E — 指派會員權限

確認 / 調整組別權限
/admin/roles 選一個組別按「編輯權限」，逐條權限鍵設定無／僅限自己／具備。
建立或編輯會員
/admin/members/new 或 /admin/members/[id]，「權限」欄位選一個組別。
確認生效範圍
同一個組別可以套用在多個會員身上；改組別權限會影響所有套用該組別的人。

05會員登入前後的差異

因為 previewMode 目前鎖 true，「需要登入」目前不會真的擋人—— 訪客一樣能點進 /wallet、/orders 這些頁面。真正能在瀏覽器上看到差異的， 是 Header 右上角頭像按鈕做的登入狀態預覽切換（存在 localStorage 的 mymeal-demo-authed）：

訪客（未切換 / 未登入）

  • Header 右上角顯示「登入」「申請帳號」兩顆連結
  • 沒有通知鈴鐺、沒有頭像
  • 側欄沒有「會員錢包」區塊
  • previewMode=false 時（尚未啟用）：側欄會出現「訪客瀏覽中」提示，需要登入的項目點了會被導去 /login，且項目旁會顯示鎖頭圖示

已登入（預覽狀態）

  • Header 顯示通知鈴鐺（含未讀紅點，點開下拉清單）+ 圓形頭像
  • 點頭像＝預覽用「登出」，切回訪客畫面
  • 側欄最上方新增「會員錢包」卡片，顯示目前餘額，點擊連到 /wallet
  • previewMode=false 時（尚未啟用）：需要登入的項目才能正常進入、不再顯示鎖頭
怎麼測試

打開任一前台頁面，點右上角圓形人像圖示即可在兩種狀態間切換；狀態存在瀏覽器本機，重新整理不會消失，但只是預覽用，跟真正的帳號驗證無關。

跟真正上線時的落差

目前的「已登入」預覽是全站共用同一個開關，不分「誰」登入——沒有目前使用者的真實 ID、看不到自己的真實錢包餘額或訂單 （側欄錢包卡片的金額是寫死的 NT$ 415）。要換成真的登入系統時，除了接 Auth.js／NextAuth 之類的驗證， 還需要把 app-shell.tsx 的 previewMode 關掉， 並把 Sidebar／Header 目前吃 localStorage demo 開關的地方，換成吃真正的 session（例如目前使用者的 Member.id 帶出真實餘額）。

MemberItemBreakdown衍生 / 非儲存

由 memberItemBreakdown(id) 把某會員的 MemberOrderRecord 依品項彙總算出：itemId, itemName, category, tags, totalQuantity, orderCount，依總訂購數量排序。這是「會員洞察 → 訂餐紀錄」頁籤實際顯示的資料。

MemberLedgerRecord衍生 / 非儲存

由 memberLedger(id) 把 MemberTopupRecord（儲值）跟 MemberOrderRecord（消費）合併、依時間排序、算出每筆之後的balanceAfter（起始基準 500）。欄位：id, type（topup/spend）, detail, amount, at, balanceAfter。這是「會員洞察 → 儲值紀錄」頁籤的資料來源。

ItemStat衍生 / 非儲存 — 跨全部會員彙總

由 itemStatsList() 把「全部會員」對同一品項的訂購與評分彙總：itemId, itemName, price, totalQuantity, orderCount, avgRating（可能 null）, commentCount，依總訂購數量排序。這是「餐點統計」列表與首頁輪播「熱門品項」的資料來源。

ItemCommentEntry衍生 / 非儲存

由 itemComments(itemId) 找出某品項被所有會員留下的評論，依時間新到舊排序：memberId, memberName, text, stars, at。用在「餐點統計」詳情頁、以及前台「所有品項 / 我的收藏」的評論彈窗。

08整體建議與方向

依優先度排列，前面是接下來動工建議先做的，後面是可以晚一點再處理的體驗優化。

P0 — 沒有這個，其他都是空談

P0

接上真正的登入 / Session

把 previewMode 關掉，Header／Sidebar 現在吃 localStorage 的地方改吃真實 session；沒有這步，「登入前後差異」永遠只是預覽切換。

P0

資料庫落地

把第六節的表建成真正的 Postgres schema（先前規劃已定案：Prisma + Postgres）。MemberInsight 系列建議拆成真的 orders / favorites / comments / ratings / topups 表，衍生表全部用 view 或查詢時 group by，不要真的存。

P0

金額改成整數分

目前 price / amount 全部是元（number），照先前規劃改成分（cents）存整數，避免浮點誤差，尤其儲值 / 消費流水帳這種要對帳的地方。

P0

錢包 / 經驗值改 append-only

memberLedger() 已經示範了「餘額用流水帳算，不直接改欄位」的概念——這應該變成正式的 wallet_ledger 表設計，Member.balance 只是快取欄位。

P1 — 現有功能裡明顯還沒接的洞

P1

「儲存 / 建立 / 刪除」按鈕還沒串接

後台大部分表單（新增組別、新增店家、編輯模板…）按下去目前沒有效果，是預期中的下一步，但要盤點清楚哪些頁面還缺 API。

P1

圖片上傳只是本機預覽

ImageField 目前用 URL.createObjectURL 做本機預覽，選檔沒有真的上傳；品項、會員頭像、蓋台廣告都共用這個元件，接後端時一次修好三處。

P1

訂餐專區沒有真正的前台頁面

/admin/zones 管理的專區目前沒有對應的 /z/[slug] 前台頁，也沒有「建立後自動出現在前台左側導覽」——這是先前討論過但特意延後的項目，建議排進下一輪。

P1

通知系統目前是純 UI

Header 鈴鐺清單是寫死的三則假資料。要做成真的，需要：後台可以手動發送 / 排程通知（例如新品項上架）、新會員註冊自動收到一則操作說明、通知已讀狀態存在會員身上。

P1

「一般使用者」組別權限全空

目前 5 個組別裡「一般使用者」12 條權限鍵全部是「無」，這符合預期（一般會員本來就不需要後台權限），但建議在權限矩陣頁面用文字註明，避免被誤會是漏設定。

P2 — 值得做但不急

P2

會員洞察的「特別標記」

目前用「推測偏好」自動算出最愛品項類型；如果要做到「手動標記這個人不吃牛」，需要在 Member 或 MemberInsight 上加一個 dietaryNotes 之類的欄位，讓後台可以直接寫備註，而不是完全依賴自動推算。

P2

命名一致性小整理

「品項標籤」頁面標題已從「標籤群組」改名，但頁內個別實體仍叫「標籤群組」（例如「新增標籤群組」按鈕）——這是刻意保留的層次差異（頁面 vs. 資料概念），但建議在文件或頁面上加一句說明，避免後續開發者誤改。

P2

團訂「查看/加入」與「加入我的訂單」已經是同一頁

曾經考慮過另外做一個獨立的加入訂單頁，後來確認 /group-orders/[id] 本身已經內建點餐表單——之後如果要重構，記得這兩者不要拆成兩個頁面，避免邏輯重複。

P2

行動裝置與列印

後台表格在小螢幕上目前靠 overflow-x-auto 橫向捲動，堪用但不理想；如果後台會有人用平板操作，建議規劃一版窄螢幕專用列表卡片。

01 組織與權限模型

會員的「部門/單位」跟「權限」是兩條獨立的軸線：部門/單位決定「這個人屬於哪個團隊」 （開團訂餐、部門彙總報表要用），角色決定「這個人在後台能做什麼」（沿用既有的 permissionGroups / memberGroups 設計，key + none/own/full 三段式）。

04 命名規則

整份規劃統一套用以下規則，之後新增 collection／欄位都照這幾條走。

01
Collection 名稱：小寫、底線分隔、複數
例：group_orders、menu_items（不是 GroupOrder 或 groupOrder）——跟 JS 變數命名（camelCase）明確區分開，一眼就知道這是資料庫層還是程式層。例外：member 這張表是單數（已在 Atlas 上直接改名），不是照這條規則的 members，其餘表仍照複數命名，不用跟著改。
02
欄位名稱：camelCase
例：employeeId、createdAt——跟現有 lib/mock.ts、TypeScript 介面的命名習慣一致，讀出來不用再轉換命名風格。
03
參照另一個 collection 一律用 xxxId 後綴
例：unitId、supplierId；一對多用單數（一筆開團只有一個 unitId），多對多用複數 + Ids（例 templateIds）。
04
時間戳一律用 Date 型別，欄位名固定幾種
createdAt / updatedAt（建立與最後更新）、at（歷程型 collection 裡「這件事發生的時間」，比 createdAt 更直覺）。不要各表自創 date、time、timestamp 混用。
05
快照欄位要explicit命名，不要讓人誤會是即時查詢結果
例：group_orders.lines[].memberName 是下單當下的姓名快照，即使那個人後來改名，這裡也不會跟著變——沿用現有 v0.3 已經決定的「存名稱/價格快照」原則。
06
該內嵌就內嵌，不是每種關聯都要開新 collection
判斷原則：這份子資料「只在父文件底下才有意義、不需要被單獨查詢或跨父文件搜尋」→ 內嵌（如 menu_templates.sections、group_orders.lines）；「需要獨立查詢、有自己的生命週期」→ 開獨立 collection（如 item_reviews 需要「查某品項的所有評論」）。
07
歷程／稽核類資料只增不改（append-only）
wallet_ledger、audit_logs 一旦寫入就不能再 update，要修正就再補一筆反向紀錄——這是先前 v0.2 規劃就點名 PHP 舊系統「刪除不會重算任務/經驗」的 bug 對策，延續下來。
08
同一個功能領域的表，用共同前綴分組（member_ / menu_）
參考舊系統 訂餐網站資料表.xlsx 的實際命名：PHP 版本本來就用 member_balance、member_experience、member_permissions 分組會員自身的狀態資料，menu_categories、menu_dishes、menu_comments 分組菜單相關資料——這份規劃延續同樣的分組邏輯：member 本身當作該群組最核心的表不加前綴，衍生／參照它的組織資料才加 member_（member_departments、member_units、member_roles）；品項相關的表都加 menu_（menu_items、menu_categories、menu_tags、menu_templates）。不是每張表都需要前綴——像 suppliers、interstitials、audit_logs 這種自成一類、沒有同群表的，維持原名就好，硬加前綴反而沒有意義。

06 延伸／待決定：任務與經驗值系統

參考 訂餐網站資料表.xlsx 時發現舊系統其實有一整套遊戏化機制（每日/每週/每月任務、 經驗值、等級），對應 daily_tasks、exp_rules、member_levels、 member_experience、member_exp_history、member_task_completions 六張表。目前這份規劃沒有把它們排進前面的 17 個 collection——這不是漏掉， 是延續原本 v0.2 規劃就留著的開放問題：「要不要保留遊戏化機制？」還沒有定案。 後台雖然有「任務與經驗」這個 nav 項目，但目前還沒有實際功能與資料。

如果之後決定要做，會沿用同樣的 member_ 命名習慣：例如 member_experience（目前經驗值＋等級，可考慮直接當 member 的欄位而非獨立表， 比照 balance 的做法）、member_task_completions（任務完成歷程，append-only）、 daily_tasks / exp_rules（任務與經驗規則的設定表，不屬於 member_ 群組， 因為它們是全站共用的規則定義，不是某個會員的個人資料）。真要做的話再另外討論，這裡先記錄舊系統的設計讓你參考。
＊此頁為規劃參考文件，尚未全部落地——目前只有 member 真的建在 MongoDB 上。
